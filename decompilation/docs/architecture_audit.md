## 0. Executive summary

- [C] Runtime C++ is **157,387** lines (qt_runtime/src 56,725 + src 66,603 + include 34,059) vs **44,155** lines of gameplay Lua (of which 15,032 are `scripts/data/`). Logic-only Lua is ~29k, so C++:Lua logic ratio is ~5:1, inverted from the agreed design.
- [C] Much of the C++ is not *live* game logic but **dead/test-only "conversion" code**: C++ combat math/resolution (1,639 lines), inactive purchase converters (346), legacy entity action service (222) and effect-spawn converter (115) have no Qt runtime caller — only conversion tests (see §2.2 "Dead").
- [C] **Redundancy clusters that cause cross-scene ripple bugs:** (1) attack delay/lockout `0xABFC` formula in both Lua (`actor/delay.lua`, `actor/actions.lua`) and C++ (`src/entities/entity_delay_conversion.cpp`, called directly from `field_scene_runtime_player_actions.cpp:989-1045`); (2) shared PRNG `0x0D44/0x0D3A` consumed from ~20 field-runtime call sites, ~15 `src/` files and ~10 Lua modules, plus a second copy of the thresholded-dice loop (`random_conversion.cpp` vs `combat.lua:169-207`) and a local recurrence in `effects/screen_effects.lua`; (3) menus/inventory/shop: Lua route+screens and a C++ `legacy_open/legacy_advance` path plus C++ inventory/shop/purchase rules; (4) spawn setup split across C++ record materialisation and Lua descriptors; (5) exit prompts chosen by both Lua building data and a C++ fallback table.
- [H] Removable or movable: ~4–6k lines from the field runtime, ~0.9–1.5k from the scripting runtime/loader policy, ~2.9–3.4k dead/test-only conversion code (plus their conversion tests), ~6–11k from test restructuring. **Total ≈ 14–22k lines**, not counting the archive.
- [H] The 2 MB ROM comparison: the realistic floor is set by tests and data, not game logic; a well-shaped port would be ~25–35k C++ host + ~35–40k Lua logic + generated data.

## 4. Target architecture shape [H]

**Thin C++ host (~25–35k target):**
- `host/app` — Qt window, frame pacing, input edge sampling (`0x195C`), headless mode.
- `host/video` — VDP name-table/sprite/CRAM projection, palette fades as a primitive, painters (field, HUD, menus) driven by Lua view-models.
- `host/audio` — SMPS/FLAC playback, music latch (`0x2830/0x2900`), fade primitive; no "when" policy.
- `host/assets` — asset catalog, TSV/JSON loading, save-file IO.
- `host/collision` — tile/object collision queries (`0xE7C8/0xE83E/0xE8A0`), returning facts only.
- `host/rng` — the **single** PRNG state (`0x0D44` step, `0x0D3A` bounded sample), exposed to Lua as the only sampler; no C++ gameplay callers.
- `host/lua_bridge` — typed DTO marshalling (today's `game_script_runtime.cpp` minus policy).

**Lua (one module per game system, E.* enums):** `actor/*` (heartbeat, think, movement/pathing, targeting, actions, delay/lockout, anim), `combat` (all rolls, damage, dice), `spawn` (default actor lists `0x43B6/0x16854/0xA800`, encounters `0x1E166/0x59986`, pedestrians), `scene_flow` (exits, doors, building return `0xBC36/0xBD34`, transitions, music selection), `dialogue_*`, `menu/*` (sole menu path), `inventory`/`shop`/`karma`, `runs/*`, `matrix/*`, `effects/*`, `data/*` (generated only, from ROM tools).

**Rules:** C++ never makes a gameplay decision or calls the RNG for gameplay; each ROM routine has exactly one port owner (enforced by the ROM coverage table §5).
